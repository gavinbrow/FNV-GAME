# Cached CODE frontier inventory

`tools/rebuild/cached_code_frontier_inventory.py` plans the fixed accepted V11
578-CODE frontier from saved metadata. It does not inspect original objects,
source bodies, archives or the reference image, run native tools, emit CODE,
create a certificate, or grant provider, application or runtime admission.

The operation pins the V11 groups/review, four distinct original certificate
authorities (205 + 10 + 54 + 259 = 528), the accepted lossless binding cache,
and original selected/native-proof metadata. The prepared collision epoch is
rebuilt from the accepted 14,471/14,477 parent plus the explicit typed COMDAT
handoff, giving 14,472 ordinary names and 14,478 collision exclusions. Existing
records, typed-negative identities, eight blocked COMDAT roots and three
canonical-reference-group quarantines retain their evidence and limitations.

Every CODE demand receives one planning row. Prepared, quarantined, unknown
namespace and cached-negative rows remain ledger-only. Only new selected roots
and unprepared cached bare-positive roots request metadata qualification. An old
positive observation still requires fresh native classification; an old negative
is preserved without constructing a replacement certificate. Generic undefined
names are not rebound by address proximity or spelling.

`prepare_metadata(operation, inputs)` admits same-byte hash-bound JSON and
computes the complete ledger and hydration request without frame decompression.
This is also the narrow independent input-review seam. `run(args)` is behind a
separate independent review bound to the exact operation, owned sources and
producer hashes. The source owner cannot sign that review. Input review and the
coordinator's once-only metadata operation require their resource leases.

For each requested recipe, the runner calls `build_recipe_contexts` once. The
frozen full-recipe reader retains unrequested owners' incoming rows, original
global row identities, missing rows and unknown future fields. Singleton and
recipe-union contracts are built by the frozen constructor with explicit new
inventory provenance. Their new metadata contract hashes are not represented as
historical certificate contract hashes. The exact generated request-file byte
hash, including its line ending, binds that provenance.

Planning cohorts are disjoint: no binding rows/native coverage unknown; recorded
missing rows; recorded parent EH; recorded omission proof rows; or field rows.
Every overlapping evidence count remains visible. These counts are not additive
unlock estimates. In particular, frozen `fields_complete` flags and an empty
binding bucket do not prove zero native relocations, closure or eligibility.

Cache receipt/index bytes are authenticated against the accepted producer and
outcome. Each requested full recipe frame freshly verifies compressed bytes,
decompressed raw bytes and semantic global-ordinal row identities before use.
Selected compressed ranges are rehashed before and after receipt publication;
data-file stat identity is tracked separately. The complete data SHA is explicitly
receipt-expected, not freshly verified. Unrequested frames are not claimed fresh.
No full-cache or original global binding/owner stream traversal is performed.

Contracts stream to private `metadata-contracts.jsonl.gz`; each compressed write
is checked before it can cross the 128-MiB output cap. The 900-second and 1-GiB
bounds remain in force. Recipe-local full contracts and serialization buffers are
released between recipes. Oversized or corrupt evidence aborts instead of being
truncated, omitted or retried. Empty hydration produces an explicit empty stream
and complete ledger, with no recipe reads.

The frozen atomic publisher is reused with additional selected-range and exact
terminal-receipt-byte postgates. Failed postgates retract the successful-name
link, preserving an aborted private attempt. Metadata/output fingerprints and
source snapshots remain independently reviewable. Prepared counts never infer
the current application cohort or runtime readiness.

The CLI accepts `--operation`, `--operation-sha256`, `--review`,
`--review-sha256` and `--out`. The closed operation schema, authoritative SHA
constants and strict review schema are defined in the source. The planned output
is `build/rebuild/cached-code-frontier-inventory-v11-v1`. No actual saved-input
or production result is claimed by these source/authored tests.
