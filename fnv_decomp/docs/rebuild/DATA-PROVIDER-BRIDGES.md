## Concrete bridge records

Each record needs a unique bridge ID, coordinate-space ID, direction, exact old
demand/base/target, input artifact/member hashes, original and serialized
physical indices, source field proof ordinals/hashes, target section/value,
representation/addend bits, ownership relation, original/input/output namespace
dispositions and false runtime/ABI/lifetime flags. Records must distinguish
an address alias from an allocation and show one canonical storage owner.

### Alignment phase before a storage alias becomes a provider

For this exact whole fragment, the original start is `0x01183000`: residue zero
modulo 4,096 and modulo 16. The current native-checked COFF contribution has
`ALIGN4096` (`0xc0d00040` flags), and its arena anchor is section 1/value zero.
An actual new contribution anchor at zero modulo 4,096 therefore preserves every
interior address residue for all power-of-two alignments through 4,096:
`(old_start + delta) mod A == (new_anchor + delta) mod A`.
No leading padding is needed for this exact input.

This is an explicit phase proof, not a type inference or an observed final VA.
A future map/PE check must establish the actual input-contribution anchor and
alignment, not merely the containing output section's page alignment. Reject
weakened contribution alignment, a shifted anchor or incompatible merge/layout
options. Object-specific requirements above 4,096 remain unknown; encountering
one blocks this v1 contract until separately proved. Storage identity and this
bounded residue guarantee do not approve arbitrary object ABI or lifetime.

Do not generalize the result to the two small alignment-one DATA fragments or
other arenas. If an original start has a nonzero required residue, simply
overaligning a new zero-offset contribution can break previously aligned
interiors. A separate successor-layout contract would need reviewed leading
storage padding and a biased coordinate anchor, or a proved maximum required
alignment phase. That would shift payload/relocation offsets and anchor/view
algebra explicitly while preserving original logical payload identity; it is
not permitted implicitly by a symbol-only bridge. No code filler, guessed type
or original-VA fallback is acceptable, and no such padding is applied here.

### Forward DATA to CODE: 13 aliases in ten member copies

Append each new `_fnv_address_v1_` name as an EXTERNAL same-section alias at the
exact accepted CODE root's output section/value. Preserve its canonical CODE
export. No original VA, copied original executable bytes, wrapper, new code,
function slicing or four-role renaming is involved. The DATA relocation already
has zero addend and continues to reference the same new address-demand name.

Never mutate the accepted CODE archive. A later producer may create a successor
archive in which exactly those ten member copies have the 13 added aliases and
every other member is byte-identical. Original code/literal payloads, section
metadata, relocations, primary/auxiliary indices and existing strings remain
unchanged; only appended symbol/string records and necessary container/export
indices change. A strict independent archive reparse must prove both indices,
all member hashes and the complete old-plus-13 export set. The original and
successor archives are mutually exclusive inputs, not two competing providers.

No emitted root becomes ABI-approved because its address can be named. Existing
source/byte comparison and native metadata evidence support this mechanical
alias; frame, caller, CRT, object and lifetime closure remain separate.

### DATA self-storage: 406 existing undefined records become views

For each exact target inside `0x01183000..0x011c16bc`, define the existing new
address-demand record in a successor DATA object as EXTERNAL, section 1, value
`target - original_arena_start`. Keep its original symbol index and all 737
relocation target indices unchanged. These are interior address views of the
one full raw allocation, never separate four-byte objects or absolute symbols.
The old object and its successor cannot both be active allocations.

This permits cycles/self-pointers without putting old VAs back into fields.
The 13,869 raw relocation fields remain zero in the object; a later normal
linker would resolve the section-relative definitions. All initialized payload,
relocation records, flags, alignment, anchor and compiler metadata stay unchanged.
Only the exact 406 symbol SectionNumber/Value pairs may change in this step.

### Reverse CODE to DATA: 119 aliases, original addends preserved

The accepted CODE union obligations contain 267 DIR32 fields whose authentic
original base and final target both lie inside this same raw allocation. Define
their existing `_fnv_undefined_(original_base, data)` names as extra same-section
aliases at `base - original_arena_start`. Do not rename or retarget any CODE
record. The 119 new alias names share the existing storage and any new-address
view at the same offset; they do not create duplicate active owners.

The saved addend distribution is 251 zero, six +4, five +8, one +12, one +24,
one +264 and two raw `0xffffff28` values representing -216. For every field the
metadata join checked both `uint32(base + raw_addend_bits) == original_target`
and the signed-offset form, with final arena offset strictly inside the same
raw allocation. No candidate crosses its boundary. Preserve the actual 32-bit
addend bits and let the normal relocation algebra apply them once.

For source expression `B + a = T`, the existing CODE name for `B` maps to arena
offset `B - start`; its unchanged field addend produces `T - start`. An exact
new address demand for `T` has addend zero and maps directly to `T - start`.
Aliasing the latter to the base offset would be wrong when `a != 0`, as would
adding `a` again. Bridge records must preserve both names/expressions and the
same physical owner. No cross-domain, one-past or tagged arithmetic is inferred.

### Small DATA16 and fresh runtime state

including their 16 existing canonical views. Keep both small objects untouched;

literals and virtual-zero storage remain separate domains. None of these

executable demands remain undefined until their explicit CRT contracts pass.
No source-literal alternative becomes a DATA allocation through this bridge.

whole-DATA, accepted CODE coverage/union/native receipts and small-DATA maps.
