# Batch 8 default-promotion review

Status: resolver review pending availability; this file is a read-only review, not evidence of an integrated promotion or a fresh build. The user delegated judgment on the verification gate. The project can document a completed, verified Phase 1 **implementation milestone** after its stated build and gameplay criteria pass, with an explicit list of deferred work. The original broader Phase 1 objective of defining all globals remains open: unresolved declarations, aliases and object extents, BSS layout/definitions, file-backed zeros beyond the selected set, W scaffold source identities, and produced-but-unspliced or rewritten ranges remain distinct. ## `--skip-data-v1` hazard

In the current driver, `FNV_M3_DV1=1` sets `DV3_SKIP` to `m3/gen/skip_ranges_b5.json`, but `--skip-data-v1` also skips `dv1_splice.py`, the producer of that combined skip file and `dv1_pieces.json`. Downstream snapshot/image paths can consume artifacts from an earlier selection, M3 configuration, object compilation, or EXT setting; the saved `dv1_log.json` may similarly misrepresent current provenance. Range validation and byte equality alone do not prove the artifacts correspond to the current build. Reject `--skip-data-v1` when the resolved effective M3 DV1 mode is active, before launching build subprocesses; allow it when DV1 is effectively off. Supporting reuse later would require verified content identities for all relevant inputs and artifacts, not just existence or timestamps.

## Review criteria

- A resolver should leave its input mapping untouched and construct a separate child environment. `FNV_M3=0` must disable all M3 overlay settings and remove derived `DV_M3`/`DV3_SKIP` and child M3 variables, preventing stale inherited controls from reaching downstream tools.
- The promoted default should set the exact reviewed selection and both DV1 switches, while respecting an explicitly supplied custom selection and explicit DV1/EXT overrides. EXT must be ineffective when DV1 is off. Child environment, driver branches, and recorded provenance must all reflect the same effective values.
- Cover absent/default, explicit opt-out, custom selection, DV1 off, EXT off, disabled-with-stale-child-flags, and no-input-mutation cases. Check the selected input digest rather than only its filename; test the `--skip-data-v1` rejection against effective DV1 for both default and custom selections and permit effective DV1 off.
- Test actual promoted default using fresh serialized builds, reference and relocation bytes, controls and gameplay as required by the verification report. Avoid treating resolver unit tests or an opt-in run as proof that the changed default works.

## Resolver review (initial version)

`config.py` is a pure copy-based resolver; its four existing standalone tests passed on review. It handles promoted defaults, custom selections, DV1 and EXT overrides, empty values, and removal of inherited `DV_M3` / `DV3_SKIP`. It is not yet integrated into the driver.

One cleanup gap remains: with `FNV_M3=0`, the resolver retains `FNV_M3_SEL`, `FNV_M3_NEGCTL`, `FNV_M3_DV1_KINDS`, and `FNV_M3_DV1_OUT` if present. In particular the latter two are DV1 child controls and should not survive when effective DV1 is off; `FNV_M3_NEGCTL` is read by downstream verifier code, so remove it when M3 is off as well. Add explicit tests for these combinations. When DV1 is active, decide whether the diagnostic output override is supported by the build driver; `dv1_splice.py` can redirect generated files with `FNV_M3_DV1_OUT` while downstream consumers expect the standard `gen` path, so simply retaining it may again consume stale files. Fail fast or deliberately control it for a normal build.

The driver currently makes branches, passes the kinds override, and populates provenance from `os.environ`, whereas the resolver returns a new effective mapping. Integration must derive **all** those operations from the same resolved mapping and record the effective selection, DV1, EXT, kinds and negative control. The SHA constant is only length-tested; if the promoted selection is intended to be pinned, compare its actual digest to the reviewed digest and fail on mismatch. A custom selection should be recorded with its own actual digest instead of being falsely attributed the promoted digest. These are integration requirements, not claims that the resolver already satisfies them.

## Resolver re-review

The revised resolver and five standalone tests pass. Disabled M3 now removes inherited `FNV_M3_*` child flags as well as derived data-v3 flags; disabled DV1 removes EXT, KINDS, and OUT. `validate_driver_options` rejects active DV1 with either `--skip-data-v1` or an output redirect, while allowing those irrelevant settings when DV1 is effectively off. Custom selection, DV1/EXT overrides, and input immutability remain covered. This is approval of the standalone resolver for integration, not approval of an untested driver change. Integration still must use the resolved mapping for every subprocess, branch, and provenance field and verify the canonical selection digest when claiming the pinned default.

## Archived-artifact audit scope

`verify_batch8_artifacts.py` usefully checks the supplied selection digest, address/size equality with the supplied manifest, kept/drop counts, original raw bounds, three recorded rewritten intervals, cross-overlay disjointness, generator log section totals, and output PE header section sizes. It reads the PE file to parse headers; it does **not** compare actual image payload bytes or relocation bytes, validate manifest symbol/types, prove the archived files were used for that executable, or establish postprocessing attribution. Its coverage total is a range-metadata calculation. The final gate must independently bind artifacts to the run and verify image hash, exact relocation bytes, controls, repeated runs, and gameplay; the audit is not a substitute.

## Proposed driver patch review

The proposed `promotion.patch` was reviewed without applying it. It resolves promoted defaults in a copied environment, invokes the stale-artifact guard before build subprocesses, derives M3/DV1/EXT/selection/negative-control/kinds and provenance from that effective environment, records the actual selection digest, and verifies the canonical filename's digest before `m3-gen`. The explicit `FNV_M3=0` route inherits the resolver's child-flag cleanup. Existing runs that explicitly specify the final selection and active DV1/EXT retain their effective settings. These observations do not establish a successful integrated default build.

One custom-selection edge remains: `ntpath.basename(selection) == DEFAULT_SELECTION` pins any custom selection with the canonical basename, including an unrelated absolute or subdirectory path. If custom selection paths are unrestricted, identify the canonical selection by normalized absolute path instead and pin only that file; alternatively explicitly reserve the basename. The driver was not patched or built during this review. Verify the actual patched driver, promoted default and opt-out paths after the clean-repeat gate; retain prior controls and do not infer their results from this patch.

## Revised promotion and harness guard

The revised, unapplied patch pins the canonical selection by normalized absolute path, allowing a different custom path with the same basename. It retains resolved-environment mode, override, digest, and provenance behavior. The per-run PID/nanosecond tag is passed to the harness and used for its verdict path; acceptance requires both successful return code and the standalone `accepted_verdict` checks. The helper's five tests passed independently for valid normalized paths, stale or malformed verdicts, wrong executable/tag, nonzero exit, and non-boolean pass flags. The harness records the supplied absolute executable and tag, matching the helper's inputs. This binds the evidence to a run tag and executable path, not to an executable content digest.

When an output directory is reused, the proposed patch does not clear an existing `OUT/harness-verdict.json` when a new run is skipped or produces no verdict; and it copies a nonempty verdict even if the acceptance check rejects it. The summary correctly says failure, but a separate consumer of the copied file might mistake stale or rejected PASS data for this run's evidence. Clear the prior archived verdict for each run and copy only an accepted verdict, or label rejected evidence so it cannot be interpreted as a passing result. This is an archive hygiene issue in the proposed patch; the live driver was not modified here.
