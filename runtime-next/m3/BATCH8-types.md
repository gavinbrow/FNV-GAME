# Batch 8: declaration type and extent review

The Batch 7 accounting reproduces exactly: 237 intervals contain 38,230 nonzero bytes in the `multi-type` bucket; 234 intervals contain 18,330 nonzero bytes in `global-non-scalar`. These are counts of nonzero bytes in entire skipped intervals, not proven sizes of declared objects. The machine-readable `inventory/b8_type_candidates.json` records every interval, raw source declaration evidence, mangled forms, encoded type observations, and conservative declared-size agreements. `b8_type_inventory.py` regenerates it from the frozen Batch 7 inputs and read-only reference.

The Batch 7 selector strips the trailing storage qualifier when populating `forms`, then strips a further character in `decl_class`. Therefore its classification and scalar eligibility are based on truncated type codes. For example, `?DAT_00ffdead@@3HA` is a four-byte `int` declaration, but its interval was classified global-non-scalar. Bucket labels are preserved here solely to reproduce its accounting; they are not type diagnoses. Fixing classification alone does not establish valid extents, byte ownership, or permit selection.

Using full encoded type observations, 68 conflicting intervals have declarations with a common known scalar/pointer size (204 total candidate head bytes); 169 remain without even that size agreement. Another 56 intervals in the non-scalar bucket have a known candidate size (159 total head bytes), leaving 178 without one. This is a conservative lexical estimate, not a definition: pointer encodings are counted only where captured declarations all visibly contain a pointer and none visibly use array syntax. Even then it requires namespace-specific declaration review, boundary checks, content and relocation checks, and compiler verification. Unknown or conflicting types remain unresolved; no candidate is certified for automatic selection.

Where all observed sizes agree and fit, the JSON separates the provisional head from the interval after it. The latter is labeled a tail only as an accounting boundary; it may contain more objects, padding, fields, or unknown array elements. Where size is unknown, neither object end nor tail is inferred. The counts include zero bytes and cannot be added to the nonzero totals above.

Examples requiring further investigation:

- `0x01190910`: source declares both `_CommandEntry[]` and `CommandDescription[]`; its 25,608-byte interval has 15,643 nonzero bytes. Mangled `PAU...` alone cannot distinguish a pointer object from an array declaration and does not prove element count or total size.
- `0x0118e8e0`: source declares both `ScriptFunctionInfo[]` and `CommandDescription[]`; its 7,688-byte interval has 4,291 nonzero bytes. Resolve structures and extent from independent evidence before defining either.
- `0x01187ac8`: `SphereVertex[]` has unknown array bound; its 2,688-byte interval contains 2,507 nonzero bytes. The next named boundary does not prove the array ends there.

No generator, selector, game source, or shared integration file was modified. No target object was compiled or selected, no build or gameplay test was run, and no conclusion is made about whether Phase 1 is complete. The reproduced accounting and schema were checked by running the inventory tool; further placement and round-trip verification are required for actual candidates.

### Conservative head candidates

A follow-up check in `b8_types_certify.py` found 16 nonzero integer scalar heads totaling 53 bytes, recorded in `inventory/b8_types_accepted.json`. Every candidate has matching complete simple scalar declarations and unit encodings, one common integer width, aligned extent, and no overlap with Batch 7, frozen DV1/produced ranges, rewritten ranges, labels, or symbolic/original relocation fields. This does not resolve source aliases or signedness; the proposed unsigned storage type preserves the reference bit pattern. Zero-only scalar heads were excluded because ordinary zero definitions can land in `.bss`. All accepted heads here came from the multi-type bucket; no non-scalar-bucket candidate passed the full filter. The JSON's “accepted” means accepted by this inventory filter only, not compiler or placement verified.

A separate pointer check found eight explicitly pointer-declared four-byte heads with an original relocation and valid target; see `inventory/b8_types_pointer_candidates.json` and `b8_types_pointers.py`. It rejects array syntax, internal labels or competing fields, existing or rewritten ownership, and invalid targets. For example, `0x011a2224` is declared `extern char*`, has original relocation at its aligned head, and contains `0x0107f750` in `.rdata`. The pointer type and any aliases remain to be reconciled. These are evidence-based storage candidates only; generator compilation, COFF relocation/bytes, image placement, negative controls and end-to-end verification remain required. No interval tail is asserted to belong to any head.
