# Read-only player-cell probe

`direct-v1/game_state.py` provides `PlayerCellProbe(pid, executable_path)`, a context manager whose `read_cell_id()` returns a nonzero cell form ID or raises `StateUnavailable`. Pass the actual run-folder executable path used to launch the PID, not the source executable path. The probe opens the process with query-information and VM-read rights only; Toolhelp module enumeration matches the first/main module's normalized path and obtains its actual loaded base. It reads and validates the remote DOS/PE signature, x86 machine and PE32 optional-header magic then parses the loaded `.data` section and addresses the player global by its original `.data`-relative offset. It does not use a debug launch, write process memory, or terminate the process.

Evidence for the address chain:

- `fnv_decomp/build/units.json` maps all 380 symbol entries containing `g_thePlayer` to preferred VA `0x011dea3c`; the preferred image base is `0x00400000`, so its original `.data`-relative offset is `0x5ba3c` (original `.data` VA `0x01183000`). The rebuilt output relocates `.data`: the saved promoted executable has `.data` RVA `0x1000`, making its player-global RVA `0x5ca3c`. The helper reads the loaded section table and uses its actual RVA rather than the original image RVA. This is a BSS location and must be read from the live process, not the file.
- `include/PlayerCharacter.h`, `Character.h`, `Actor.h`, and `MobileObject.h` describe the primary inheritance path to `TESObjectREFR`. `include/TESObjectREFR.h` declares and statically asserts `m_pOwningCell` at `+0x40`.
- `src/fallout_shared/tesdatahandler_forms.h` declares `TESObjectCELL : TESForm`, and `include/TESForm.h` declares and statically asserts `iFormID` at `+0x0c`.

The helper reads all three 32-bit values twice and rejects nulls, zero form IDs, missing or short reads, inconsistent player/cell/form values, wrong module path, invalid header and unsupported image. Two matching reads reduce transition risk but are not an atomic snapshot. The cell ID comparison should require a stable valid value before F5, a different stable value after the cell change, and the original value after F9. This corroborates cell transition and restoration; it does not prove all game state was saved or restored. Do not accept HUD alone if the process probe is unavailable.

`python -I runtime-next/m3/tools/test_game_state.py` passes six isolated tests covering relocated base arithmetic, pointers and form IDs, null/error/short/transient reads, invalid PE or module identity, and cleanup. Tests use mocked process readers; no live process or gameplay was accessed. The helper verifies image type and path, not its content hash; the build/harness must separately bind the launched executable to its verified artifact.

## Image profile and verified run

The address calculation assumes the custom M3 image preserves the original `.data`-relative layout, including the virtual BSS tail, while allowing the `.data` section and the whole module to load at different RVAs or bases. The loaded-section lookup handles that section movement and ASLR; validating the PE header and section bounds does not prove that a different build preserves the same internal layout. In particular, a future native-link image may use a different `.data` layout and needs its own independently verified mapping before using this probe. The caller must bind the launched image to the verified build; path and PE checks alone do not establish content identity.

The saved `out/batch8-promoted-default-verified/harness-verdict.json` records a live probe result: cell `1291213` before and after quicksave, `1073541` after the console cell move and before quickload, then `1291213` after quickload with the HUD observed. Its verdict records PASS, exit code 0 and no WER events. This is evidence of cell restoration in that run, not proof of all saved state. Earlier gameplay records that only checked the HUD after F9 did not establish that quickload restored the saved cell, even if their reported HUD check passed. The six mocked tests described above remain separate from this live evidence.

This verification does not resolve original identities and types for the approximately 849 KB of W scaffolding, native symbol aliases, remaining BSS definitions, or unknown full array extents. Those remain deferred; a successful current-image verification does not establish that all M3 data has its original real source type.
