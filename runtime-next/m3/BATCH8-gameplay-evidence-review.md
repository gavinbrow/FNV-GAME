# Batch 8 final positive gameplay evidence review

This is a read-only review of `direct-v1/harness.py`, `out/batch8-final/harness-verdict.json`, `out/batch8-final/logs/08-harness.log`, and its build summary; it does not rerun gameplay. The verdict names the same final output executable as the summary. The harness copies that source executable to its isolated run directory when its bytes differ before launching it. The saved log and verdict agree on PID, timing and steps; the summary records harness return code 0 and PASS.

The saved verdict reports menu detected at 50.5 seconds, world loaded, 69.7 seconds of play with process alive, a save-file count increase from 1 to 2 with `quicksave.fos`, positive world checks following the cell console command, time change and F9 quickload, and exit code 0. No forced kill, harness error or matching WER event is recorded. In code, failure to detect the menu or initial world raises an error; the extended gate requires the new-save count and all three later world checks. The harness sends COC, F5 and F9 and performs movement/weapon inputs. A forced kill occurs only in `finally`; `exited_cleanly` is determined before that and is required for PASS, so a forced kill cannot by itself pass.

The later world checks use an on-screen HUD/color heuristic. They establish that the heuristic saw a world view after the inputs, not independently that the requested cell became active, the new save's contents were valid, or F9 loaded that specific file. The new-save check counts `.fos` files after deleting preexisting quicksave copies in the isolated run directory; it does not parse the save. The executable path in the verdict identifies the intended source file, but the verdict has no executable hash.

General stale-verdict risk remains in `build_all.py`: the harness uses a shared `build-all` tag, and the driver reads its existing verdict without first removing it or checking its timestamp or executable identity. Build status tests the loaded `pass_` value without also requiring harness return code zero. For this run, however, the matching contemporaneous log and verdict PID/step data, final executable path, and recorded return code 0 support that the saved verdict came from the final positive run. These observations do not remove the general driver risk.

## Promoted-default failed harness run

The later uniquely tagged promoted-default run `build-all-937740-1795049441781226400` failed its extended gate: the saved verdict records `new_save_written`, `world_after_coc`, `world_after_time`, and `world_after_load` all false, with exit code 0. The initial Continue confirmation, world load, and first two recorded play iterations visibly show expected screens. The first observed divergence is `05_pipboy_3.png`, which shows the pause menu after the healthy `06_world_2.png`; its cause between screenshots is unknown. The pause menu persists through the quicksave attempt and later screenshots show Controls with the console open. Preserve this failed run rather than interpreting its clean exit or matching executable as a gameplay pass.

The harness's `foreground()` injects an ALT key and does not check whether `SetForegroundWindow` succeeded. Focus loss is a possible explanation for pause, not a demonstrated cause. The isolated run's existing INIs do not contain a `bPauseOnAltTab` entry; they show background keyboard enabled and background mouse disabled. These facts do not establish the game's pause-on-focus behavior. Before play iterations and extended inputs, a bounded world-HUD check can detect the observed drift; recovery should send ESC only when a pause menu is positively identified, then require world detection, otherwise wait within a bound or fail. The existing console fallback toggles grave again whenever HUD is absent, including during loading or a menu; a conservative path should close once, wait for the expected world, and avoid toggling an unidentified state. Original save, cell/time/world and quickload checks must remain required.
