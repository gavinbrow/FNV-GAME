# Command record prefix fixtures

Two isolated fixtures establish that source-supported 40-byte record views can represent substantial accessed command-table prefixes with real symbolic pointer references. No change to the frozen Batch 8 selection or shared generator was made. Results are in `inventory/b8_command_prefix_fixture.json`; reproduce with `python b8_command_fixture.py` from this directory. The fixture uses the installed VC2008 SP1 compiler with the project unit options, then reads the resulting COFF object through `splice.slice_entry`.

| Prefix | Source-supported accessed records | Fixture bytes | Original DIR32 cells |
|---|---:|---:|---:|
| `0x01190910` | 640 | 25,600 | 3,802 |
| `0x0118e8e0` | 192 of the 205 observed accesses | 7,680 | 1,050 |

The second prefix ends at `0x011906e0`, before the existing DV1/produced record at `0x011906e8` and Batch 7 object beginning `0x011906ec`. Both prefixes lie wholly inside one `.data` chunk and avoid saved Batch 7, DV1, produced and known rewritten ranges. Neither contains internal declared-address boundaries or data labels, value-rule fields, or relocation cells with invalid targets under the current selector's target model. All non-relocated cells treated as pointer storage were zero.

The fixture record follows the 40-byte source `CommandDescription` view for `name`, `alternate`, `opcode`, and `description`, and the `_CommandEntry` view's parameter-pointer position at `+0x14`; see `BATCH8-array-review.md` for source locations and access-count evidence. It leaves `+0x10` and `+0x24` as opaque words and `+0x18`, `+0x1c`, `+0x20` as opaque pointer storage. The separate `ScriptFunctionInfo` definition documents more detailed fields, but its use here would require resolving the function-pointer and alias types. Symbolic initializer expressions point to synthetic `M3F_`/`M3D_` externs corresponding to original targets. This source view is a partial representation of known fields, not a claim that every opaque field has its original semantic type.

Both objects compiled without a dynamic initializer. Their non-relocation bytes matched the reference; every original relocation offset matched one DIR32 cell, each symbolic target matched the corresponding original value, and each addend was zero. The reference byte SHA-256 values are recorded in the JSON. These checks establish isolated object representability, not final placement, complete array size, source symbol identity, true function signatures, or a successful full image. The existing generator needs a deliberate source-supported record-array representation before selection; an untyped W conversion would lose the basis for this fixture. A future selection also needs fresh ownership checks and image verification, including negative controls and gameplay. Source-supported field and pointer storage can be done in Phase 1; exact class identities, vtables or source changes reserved for Phase 2 remain deferred pending approval.
