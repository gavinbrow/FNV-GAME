# NiRefObject visibility and physical-owner evidence

The private parent source in unit 1503 defines `FUN_00aa05a0` directly derived from `NiRefObject`, declares its own TU-local inline `NiRefObject::~NiRefObject`, and defines the mapped destructor at `0x00aa05a0`. Its source-mapped vtable at `0x010a2164` leads through original relocated COL `0x01127ba0` to TypeDescriptor `.?AVNiShaderFactory@@`; its reference hierarchy is NiShaderFactory → NiRefObject → NiMemObject with PMDs 0, 0 and +4. This supports the original shader-factory family and base subobject, without establishing every source member, virtual slot, destructor declaration, or complete class identity. In the saved parent fixture, that destructor emits 277 bytes and its NiRef cleanup is inlined: vptr store, counter address and InterlockedDecrement. Removing its local inline definition changed this mapped function to 269 bytes and replaced that cleanup with an external destructor tail jump.

The five other candidate regressions are distinct contexts, not evidence that the compiler must use the same physical cleanup body everywhere. Unit 111 (`bsbatchrenderer.cpp`) defines a `NiObject`-derived batch-renderer source view and has a 311-byte mapped destructor; unit 1200 (`nicolordata.cpp`) calls the NiObject base destructor in a NiColorData-derived shell (40 bytes); unit 1433 (`nigeometrydata.cpp`) explicitly casts a geometry-data view to NiRefObject before the destructor (341 bytes); unit 1598 (`nipsysemitterctlr.cpp`) casts a NiBoolData source view (61 bytes); unit 1630 (`nipsysplanarcollider.cpp`) uses an explicit NiRefObject cast in a holder view (69 bytes). Those casts and surrogate names are source views; they do not prove all original native class identities or complete RTTI graphs. Their original parent COFFs call the same source-mapped destructor symbol at the distinct 18-byte optimized physical owner `0x00a5d3d0`. The universal inline-header candidate changes their bodies to 313, 51, 352, 71 and 79 bytes respectively by substituting inline vptr/counter/decrement operations. These are real mapped-reference regressions.

The prior out-of-line fixture naturally emitted a 33-byte native destructor in unit 612 as strong COMDAT `NODUPLICATES` (selection 1), a 46-byte G wrapper as `ANY` (selection 2), and an E weak fallback to G (mode 2). Unit 1503 then had an undefined native destructor reference and an emitted 32-byte G wrapper with selection 2. The inline-header fixture emitted unit 612's 33-byte destructor and 46-byte G wrapper as `ANY`, and unit 1503's 18-byte destructor and 44-byte G wrapper as `ANY`; both units expose E weak fallback to G, mode 2. These same-name definitions have different bytes. None of these observations establishes which definition the final build consumes.

The currently demonstrated source-context split retains one shared class layout declaration but makes the destructor body visible locally only in unit 1503; it preserves the measured `/O2` caller forms. It is a reconstruction baseline, not proof that this is a conforming final one-definition model or the original header organization. A new global out-of-line definition conflicts with its existing local inline definition unless the declarations and definitions are reconciled; a universal inline definition provably regresses five mapped functions. The data therefore does not yet justify a single canonical source-body model that preserves all six measured cases. A renamed adapter, duplicate class, forced compiler attribute, or same-address binding would require its own source/RTTI/ABI evidence and is not adopted here. The separate unit-2725 physical 18-byte owner remains untouched. Broader 119-unit source closures, actual compiler traces, class identity, weak/COMDAT selection and final placement remain open; the separate 38-source proposal is unaffected.

## Archived physical-owner callers and declarations

The private Calendar-bound recipe contains 75 per-unit symbol mappings in 64 units to `0x00a5d3d0`, and 20 mappings in 17 units to `0x00496910`. These maps include differently named source views and are not global class-identity evidence. `niref_archived_physical_callers.py` checked only matching units for which the independently hashed 825d or 6757 object archive exists. Its private output `../out/phase2-niref-primary-inline-fixture/archived-physical-owner-callers.json` records 44 actual mapped-function REL32 fields in 34 archived units: 33 map to `0x00a5d3d0` and 11 to `0x00496910`; 31 are call opcodes and 13 are jumps. Forty-seven alias-bearing units lack an object in those selected archives, so this is not a complete caller census. The five original callers regressed by the universal-inline experiment are among the archived calls to `0x00a5d3d0`.

The physical 18-byte owner in unit 2725 is a source-local `class FUN_00a5d3d0` with a virtual destructor and `DeleteThis`, a four-byte reference count and a static `long` counter. It does not declare the canonical NiMemObject base in that view. The saved object emits its destructor under a distinct external source symbol in a COMDAT with `NODUPLICATES` selection; its relocations point to that view's mapped NiRef vtable, counter, and InterlockedDecrement import. The primary unit-612 33-byte surrogate is likewise external and `NODUPLICATES` under a different source symbol, with a mapped vptr, counter and atomic-helper call. Their equivalent cleanup intent is supported, while source class/base declarations, signed counter views, optimizer visibility and actual final linkage remain different facts.

No additional one-class implementation test is justified solely by these physical mappings. The existing 1503 local inline body and five out-of-line callers preserve measured code but are not a proven ODR-complete original class model; globally visible inline and external alternatives each demonstrably change at least one mapped caller. An eventual next source experiment needs an independent original declaration/visibility or provider-ownership premise and must preserve the separate physical `0x00a5d3d0` and `0x00496910` functions. No noinline directive, invented protocol or reference-only name binding is proposed.
