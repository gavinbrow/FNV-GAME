# Unit 425 `GetPartName` conflict

The two source views use the same original machine routine for different object layouts. Unit 425 maps `?GetPartName@BGSBodyPart@@QAEPAUNiAVObjectS@@XZ` to `0x006838b0`; unit 621 maps `?GetPartName@BGSBodyPart@@QAEPBDXZ` to the same address. This is not evidence that the true BGSBodyPart method returns both types.

Original `0x006838b0` adds `0x1c` to `this`, calls `0x00559450`, and returns its result. The latter returns the first pointer-sized member of its input. A generic pointer getter at the same offset can therefore serve unrelated classes when code is folded or deliberately reused; this behavior alone does not identify the enclosing object's type or the pointer's semantic type.

The actual unit 425 source call is in `FORenderedMenu`-derived `FUN_007ff740_shell::UpdateBodyPart` (`forenderedmenu.cpp:3024–3035`). It casts the menu `this` to a fabricated global BGSBodyPart view, calls `GetPartName`, and uses the result as a `NiAVObjectS*` to invoke object methods. The reference at `0x007ff74c`, `0x007ff75a` and `0x007ff77f` calls the same getter on the saved menu `this`; its nonnull return is then used as `this` for calls `0x00450f90` and `0x00a59c60`. The object-pointer use is real; the source's BGSBodyPart type/name is a cross-class adapter, not proof that the actual BGSBodyPart field is an object pointer.

Separately, unit 621's BGSBodyPart layout has `m_kPartName` at `+0x1c`, a `BSStringT<char>` whose first member is a character pointer. `bgsbodypartdata.cpp:129` passes the result of `part->GetPartName()` to a `%s` warning argument. The original `0x005e5036` calls `0x006838b0` on the loaded part, pushes EAX, then passes it to warning routine `0x005b5e40` with the mapped format. Together the source layout, string consumer and original call support a character-pointer view for this BGSBodyPart method. They do not independently prove constness or the historical source name.

Directly replacing unit 425's local class with the canonical BGSBodyPart header would leave a real return-type mismatch at its object-method call sites and an invalid cross-class cast. A possible separate private experiment is to use a uniquely named menu layout view with an object-pointer getter bound to `0x006838b0`, rewrite only those cast sites, and verify all unit 425 mapped functions, relocations and literal ownership. The actual menu member identity and source-level type still need proof; no such rewrite or binding is installed here. Unit 423 similarly casts a menu object to BGSBodyPart and casts the same getter's return to `NiPointLight*`, so its matching `const char*` declaration is not proof of a true BGSBodyPart call.
