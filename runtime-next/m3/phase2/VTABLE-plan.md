Status: opt-in weak-resolver experiment and private class overlays are in progress; no protected `fnv_decomp/src`, `include`, or `build/units.json` changes have been installed, and the promoted default selection remains unchanged. Compiler and full-build evidence is reported separately; the original camera-path candidate remains unverified and no vtable recovery is claimed.

## Existing pipeline and blocker interpretation

`data-v1/phase0.py` reads compiled unit COFF sections and resolves their relocation fields against unit mappings and existing build resolution. `data-v1/place.py` places section pieces; tier V means a unique placement by byte pattern with resolved relocations. Its `pieces.tsv.gz` records address/size/tier/kind but not unit identity. `m3/dv1_splice.py` selects verified pieces only when every relocation resolves to the reference target, original relocation sites match, full resulting bytes match, the piece fits one chunk, and ownership is disjoint. `m3/out/batch8-promoted-default-verified/evidence/` preserves the final M3/DV1 manifest and DV1 pieces. `fnv_decomp/tools/gen_function_names.py` manages one category of names; source header generation and RTTI fixture tools exist, but none is established here as a safe one-click semantic vtable repair.

The Batch 6 40,960-byte unresolved-method / `__purecall` and 30,564-byte base-method-versus-reference counts in `DESIGN-phase1.md` are first-failure **piece-byte sums**, with duplicates; they are not unique recovered bytes or a partition of Batch 8's 207,636-byte produced-but-unspliced range. `vtable_triage.py` and `vtable_triage.json` are a discovery aid only: absence of a unit-level symbol mapping does not by itself establish that the full resolver cannot resolve a name, and section remainder length is not proof of original object size. Their candidate counts are not coverage estimates.

- Offset 4 is a relocation to undefined `??_E?$NiTPrimitiveArray@PAVBGSCameraPath@@@@UAEPAXI@Z`, not mapped under that exact spelling in any unit symbol table or function list. The original target is `0x0058bc90`. `src/CameraPathManager.h:12` declares a virtual destructor; `src/staging/blk_00580000_od.cpp:770` defines the uniquely listed unit-2652 function at that address as a deleting-destructor-shaped wrapper: it invokes `0x0058b830`, optionally deallocates `this` when bit 0 is set, and returns `this`. ## Deleting-destructor weak-external audit

A read-only inspection of unit 1's existing COFF object adds a specific constraint to the candidate; no compiler invocation was used. The vftable slot names `??_E?$NiTPrimitiveArray@PAVBGSCameraPath@@@@UAEPAXI@Z` as a COFF weak external (storage class 105). Its auxiliary record has search characteristic 2 and its fallback TagIndex points to an undefined `??_G` symbol of the same specialization. The same object also contains a defined `??_G` symbol in its own section 21, with a 44-byte body. This is object-specific weak-fallback evidence, not proof that the current data-v1 resolver follows the auxiliary record or that a different class uses the same rule.

The compiled `??_G` body and the existing unit-2652 implementation at `0x0058bc90` are each 44 bytes and match at every non-relocation byte. Both have x86 REL32 call fields at offsets 11 and 28. The unit-1 body calls the specialization's undefined `??1...` destructor and global `operator delete`; the unit-2652 source-backed wrapper calls `FUN_0058b830` and `_Deallocate`. Unit 2652 maps both `_Deallocate` and global operator delete to `0x00401030`; its `FUN_0058b830` maps to `0x0058b830`. No exact specialization `??1...` symbol was found in unit symbol mappings or function lists. These observations strengthen the deleting-wrapper hypothesis but do not establish that the unresolved `??1...` target is `0x0058b830`, nor that the normal resolver can derive the `??_E` fallback and final target without a reference-fed alias.

**Decision:** remain fail-closed; no source/recipe/generator change is justified yet. The smallest next evidence step is to prove the specialization destructor's target and behavior independently, then exercise weak-external fallback resolution using the real resolver and verify both call relocations. Only a candidate that passes those checks can proceed to the exclusive isolated compile lane and full-section tests. The source's `ActorCombatGroup*` allocator view also remains a type-identity caveat.

## Opt-in weak-external resolver experiment

`pinned-build/coff_weak.py` reads weak auxiliary metadata from the existing COFF object bytes without modifying `compare.Coff` or protected decompilation source. `assemble_v3.resolve_field` retains its existing direct resolver first, and only when `FNV_COFF_WEAK=1` follows a valid weak fallback via that same direct resolver. The experiment supports characteristics 1 (NOLIBRARY) and 3 (ALIAS), rejects characteristic 2 (LIBRARY) because the pipeline does not yet prove library-search precedence, and rejects missing/invalid auxiliary records, invalid indices, cycles and ambiguous fallback values. Name-embedded address heuristics are explicitly rejected for weak primaries and fallback symbols because an address in a decorated class name may refer to the class rather than the method. The original addend and normal mapping provenance are retained; no reference target is supplied as an alias. When the flag is unset, direct resolver behavior is unchanged.

`python -I runtime-next/m3/phase2/test_vtable_weak.py` passes 15 isolated tests (primary precedence, opt-in behavior, actual direct-resolver fallback and addend, supported modes, malformed records, invalid indices, cycles, ambiguous values, name-embedded heuristic rejection, and explicit rejection of this camera candidate's real characteristic-2 weak record). These tests do not invoke the compiler, full build or game. Independent review and an exclusive verification-lane build are required before any default change; the experiment has not recovered the candidate, proven library precedence, or established the specialization destructor target. A proposed verification run must start with the saved canonical baseline and check exact image/relocation bytes, no new borrowed fields and all existing semantic gameplay gates. Keep the flag unset for the accepted default until verified.
