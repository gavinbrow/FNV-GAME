# 825d native NiMemObject operator preflight

The private 825d proposal reuses the separately tested native allocation API and two owner bodies without including the 750-unit class-key hypothesis. It verifies the reviewed 6757-to-825d recipe transition semantically, confirms the two owner recipes are unchanged by that transition, and changes only the 1664/2734 owner symbols in its candidate recipe. All function addresses, sizes, flags and other unit fields remain intact.

The existing public allocation header reaches 126 lexical recipe consumers; units 1664 and 2734 newly include it, giving 128 units, 2,580 mapped functions and 88 listed EH tails. The source/include closure was recomputed against 825d for each consumer. No prior consumer closure changed across the seven-source transaction; in particular units 253, 370, 425, 620 and 2909 are outside this public-header cohort. This is static quoted-include evidence and does not replace compiler guard/first-declaration checks.

The on-demand scripts `nimem_operators_825d_prepare.py`, `_compile.py`, `_compare.py` and `_run.py` prepare minimal source mirrors, use explicit unit compiler flags and production include order, capture compiler include traces/warnings, and compare actual production/original/candidate mapped functions and ordinary EH. Generated NiMemObject/operator/deleting-wrapper sections are recorded for separate weak/COMDAT review; changed code, source baseline failures, literal labels and EH errors are not automatically normalized or hidden. The full runner requires a private archived production-object set and its manifest SHA, an exclusive build lock and explicit serialized-lane acknowledgment. No compiler run is authorized by preparing these files.

Preparation-only smoke passed for an owner and a consumer. The 1664 comparator also passed a read-only smoke using a historical production object and previously compiled, hash-identical mirrors; that is not proof of the current 825d build.
