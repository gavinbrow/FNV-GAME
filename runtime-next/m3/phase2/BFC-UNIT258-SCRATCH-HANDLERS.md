# Unit 258 scratch-array handler identity

The 157-byte unit258 `ScratchArray` helper has four relocations. Its nonrelocation bytes match both independently source-owned unit260 functions at 0x00c7d480 and 0x00c7d520. When the separately anchored original handler pointers 0x00f316b8 and 0x00f316e8 are supplied diagnostically, respectively, all four relocation fields and all body bytes match. Those handler addresses are reference-anchored evidence, not installed source mappings.

The two handlers lead to distinct FuncInfo and unwind-map records: 0x0117cb18 / 0x0117cb10 and 0x0117cb44 / 0x0117cb3c. Each has one unwind state, with distinct actions at 0x00f316b0 and 0x00f316e0. The first action jumps to source-owned 0x00629b40; the second jumps to source-owned 0x00c7b0f0. Unit258's emitted cleanup funclet uses a member-pointer load matching both original action encodings. The unit260 owner-function surrogates emit a different address-of-local instruction in that funclet, so their identical main function bodies do not establish their full exception behavior.

The emitted unit258 ArrayStorage destructor strictly matches 0x00c7b0f0 but does not match the different 83-byte 0x00629b40 destructor. Therefore one compiler-emitted ScratchArray/ArrayStorage pair cannot be mapped to both original helper/EH graphs by one normal symbol binding. A safe split requires independently supported first-object base type and lifetime semantics, exact handler and complete state-map comparisons, and all affected parent/caller checks. No fold or address alias is proposed.

The first helper's original normal path makes the same inline allocator/free calls as the second 157-byte helper. Its state-zero exceptional action instead calls 0x00629b40, whose source-owned body calls the independently mapped container-clear function 0x0062a080 and an empty base destructor at 0x00483710. Substituting that destructor as the ordinary base would change normal cleanup and is therefore not justified by the EH pointer. Recovering the first object's construction and exception-only lifetime remains necessary before proposing a type.

Further callee-chain examination changes the earlier interpretation: the two cleanups have the same observable core operations for trivial four-byte elements. The 0x00629b40 path calls 0x0062a080 and then an empty base destructor. 0x0062a080 obtains the allocator through 0x004a4840 (router 0x00c85750 then offset +0x10) and calls 0x0062a0b0. That function clears the element range through 0x0062a120; its range-destruction callee 0x0040fbe0 is an empty cdecl return. It sets size at +4 to zero, tests the sign bit of capacity +8, and when owned calls allocator vtable slot +0x10 with data at +0 and `(capacity & 0x3fffffff) * 4`; it then clears data and sets capacity to 0x80000000. The 0x00c7b0f0 optimized body reaches the same allocator and slot and performs the same capacity scaling and final field values, with the final two stores reversed. This supports an /Od versus /O2 inlining hypothesis for a trivial-element array, not proof of source-type identity or equivalence under concurrent observation.

A valid reconstruction would need a single source-supported canonical type/helper whose out-of-line /Od emission matches 0x00629b40 and whose /O2 inlining produces the 157-byte outer body, while exception unwinding binds that exact canonical out-of-line destructor and preserves the 0x00f316b0 state action. The existing unit258 ArrayStorage inline destructor currently emits the 60-byte optimized form; the unit2662 owner uses separate surrogate `Date`/`FUN_00629b40` declarations. Their common C++ type identity and inline definitions are not established. A wrapper that merely assigns one destructor's symbol to 0x00629b40, or changes only the exception action, would not supply that proof. Type/layout and source definitions, field/lifetime behavior, all affected functions, handler/xdata, relocation and source-owner comparisons must pass in an isolated compiler experiment before any binding or fold proposal.
