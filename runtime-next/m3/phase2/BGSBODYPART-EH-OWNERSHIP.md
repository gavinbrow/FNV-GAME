# TESModel cleanup target ownership

The split-header fixture changes direct destructor relocation spelling from `??1TESModel@@QAE@XZ` to `??1TESModel@@UAE@XZ`. These spellings describe different C++ declarations and must not be treated as interchangeable source contracts merely because their x86 call shapes match. The reference targets can, however, be checked independently.

For unit 620, the original BGSBodyPart constructor's handler points to its seven-state unwind map. State 5 cleans the model at `this+0x2c` by jumping directly to `0x00489070`; state 6 cleans the PSA member at `this+0x44` by jumping to `0x0051b950`, which in turn calls `0x00489070`. The original BGSBodyPart destructor also directly calls `0x00489070` on `this+0x2c`. The original unit 620 recipe explicitly maps the nonvirtual-spelled TESModel destructor to that target.

For unit 621, the original BGSBodyPartData constructor at `0x005e4af0` installs handler `0x00ef9e73`, which loads FuncInfo `0x0114b4d0`. Its relocated unwind-map pointer leads to `0x0114b4c0`. State 1 has a relocated action pointer to `0x00ef9e68`; that action loads saved `this`, adds `0x18` and jumps directly to `0x00489070`. This independently supports the candidate unit 621's virtual-spelled destructor cleanup target even though its old unit recipe does not supply that name. The original source unit `tesmodel.cpp:593` has a destructor-view body at `0x00489070`; `tesobjecttree.cpp:181` has a `0x0051b950` helper view explicitly calling the TESModel destructor. These views support behavior, while original C++ access, virtuality and symbol spelling remain separate questions.

The implicit PSA destructor and scalar deleting wrapper in the compiled split object independently match the original `0x0051b950` and `0x005e3c30` code outside their relocation fields; original REL32 targets are `0x00489070`, and `0x0051b950` plus `0x00401030`, respectively. The object's vector-deleting weak external names the scalar wrapper as fallback with characteristics 2. Actual linker fallback, record ownership and all candidate EH relocation targets still require final-build verification.

The native BGSBodyPart destructor candidate is separately staged and frozen under `out/phase2-bgsbodypart-native-destructor-proposal`. It retains the `0x005e3d50` helper call and keeps unrelated wrappers separate. It is not compiled at the time of this note; its member cleanups, EH and vptr store require direct comparison before replacing the existing adapter.
