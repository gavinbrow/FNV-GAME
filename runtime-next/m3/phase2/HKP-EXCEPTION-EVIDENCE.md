# hkpConstraintViewer constructor exception evidence

The original unit 2501 and its first hierarchy hypothesis each emit a 112-byte constructor; the isolated hierarchy comparison matches the original reference. Neither object has a constructor EH-handler symbol. The destructor-aware v2 overlay emits 175 bytes and an EH handler whose cleanup relocations reference both `hkpWorldViewerBase::~hkpWorldViewerBase` and `hkpWorldPostSimulationListener::~hkpWorldPostSimulationListener`; it also references `__CxxFrameHandler3` and security-cookie support. This establishes the source of extra compiler machinery, but does not prove which original exception settings or contracts produced the reference.

The base constructor maps to 0x00ddccb0 and the listener registration method to 0x00c93920. Related decompiled viewer surrogates declare each as `throw()` (`hkpphantomdisplayviewer.cpp` and `hkpsimulationislandviewer.cpp`). The 0x00c93920 implementation in `hkpworld.cpp` may grow an array through `ResizeAudioStream`; local allocator declarations are inconsistent and do not establish a semantic no-throw guarantee. These source declarations are useful code-generation hypotheses, not original exception-contract proof.

`rtti_hkp_exception_hypotheses.py` produces three isolated pinned alternatives that vary only the two related-source declarations, individually and together. They are uncompiled and do not change compiler flags. A later exclusive compiler experiment should compare the constructor and all 16 mapped functions, EH handler/relocations, original reference, hierarchy and complete observed slot data. Even an exact match does not prove safety of throwing through the reconstructed hierarchy; native integration remains blocked on class, destructor and ABI evidence.
