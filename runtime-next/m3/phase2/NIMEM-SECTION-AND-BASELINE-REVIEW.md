# NiMem section reviewer and combined-lane provenance review

`nimem_kind_section_review.py` reads COFF section-definition auxiliary fields at the standard 18-byte symbol-record offsets (`<IHHIhB`) and weak auxiliary target/mode at `<II`. Counters correctly account for duplicate section records. Relocation records retain offsets, types, symbol names and addends via the original section data; section characteristics are compared. Checksums are deliberately omitted, and associative COMDAT partner identity is reduced to a normalized symbol-name multiset, so the test cannot establish final linker/provider ownership or disambiguate all same-named sections.

The reviewer must fail closed before use as an acceptance gate: terminal progress must explicitly require a successful status, unique unit IDs and the exact expected cohort; each compile must have exactly one original and candidate, and comparison status/results must be checked. Pin and revalidate the source snapshot and tool/compiler identities, and rehash the object and comparison inputs at the end, not only the progress file. Normalize descriptor bytes only within a verified NiMemObject type-descriptor record: currently global `.replace` across every nondebug section can hide the same byte pattern in an unrelated object. The script can still provide useful diagnostic counters, but a mismatch is not a pass and equality alone cannot establish type identity or final COMDAT placement.

The seven combined-lane baseline objects were copied from `runtime-next/pinned-build/obj_v3` at 10:46:28 UTC; their exact hashes and source mtimes are preserved in `../out/phase2-source-integration6757-lane/capture.json` and per-unit manifests. The accepted default archive saved only objects 0002, 0998, 1111 and 1112, and its compile log did not capture hashes of these seven. Thus the mtimes and source/recipe freeze support, but do not cryptographically prove, identity with the objects consumed in that default build.
