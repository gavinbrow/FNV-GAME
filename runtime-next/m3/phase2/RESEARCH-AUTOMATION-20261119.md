# Non-AI class recovery automation: bounded assessment

Research date: 2026-11-19. This is a source/documentation review and a proposed benchmark, not a tool run or a recovered-class claim. No tool was installed, downloaded, compiled or executed against the game.

## Recommendation

Start with the existing local, read-only evidence pipeline and make a small, context-aware source-view inventory before adopting a new reverse-engineering platform. `runtime-next/m3/phase2/native_class_inventory.py` parses observed x86 RTTI graphs and explicitly does not infer source signatures or vtable extent; `class_metadata_compare.py` compares native COFF records and slots using existing source-unit mappings without inventing aliases. `rtti_scoped_registry.py` and `rtti_header_resolution_audit.py` are existing relevant discovery points. The current verification plan already records typed RTTI/vtable pieces and unresolved class-vs-struct names, destructor/weak symbols and inherited-vs-overridden slots. A second RTTI inventory is useful only if it supplies a concrete missing fact, such as an independently supported destructor association or field constraint.

For source conflicts, the smallest prospective increment is an **evidence index**, not automatic class merging: for a bounded list of translation units, retain exact source path/hash, include resolution/order, preprocessor context, declaration kind, namespace, bases, fields, virtual signatures, packing/assertions and source locations. Join those records to the existing reference RTTI/COFF census by explicit evidence, not spelling alone. Preserve unsupported or conflicting cases as separate rows. Only after an isolated compiler and existing exact byte/relocation/EH checks pass should a rule emit a reviewable source proposal; recovered names alone are not an accepted native type.

## Tools and tradeoffs

| Tool | Verified capability | Practical fit and limits |
|---|---|---|
| [Ghidra RecoverClassesFromRTTIScript](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/Decompiler/ghidra_scripts/RecoverClassesFromRTTIScript.java) | The actual upstream script calls itself a prototype and uses RTTI to infer hierarchies, inheritance, constructors/destructors and data types; it runs the Windows RTTI analyzer when needed, supports headless branches, and modifies the Ghidra program/data-type database. It requires an already analyzed program and refuses an existing recovered-class category. | Moderate setup if an isolated, matching Ghidra project is already available; otherwise creating and analyzing one is extra work. Its graph and member hypotheses overlap existing local RTTI observations. Export would need a small read-only Ghidra script and explicit image/hash/address provenance; this is **not** currently a generator input. Use a disposable project copy because the script changes analysis state. A documented [upstream exception](https://github.com/NationalSecurityAgency/ghidra/issues/8853) and project/version dependencies warrant pinning a tested release. No measurement of its correctness on this target has been made. |
| [CMU Pharos / OOAnalyzer](https://github.com/cmu-sei/pharos) and [usage](https://github.com/cmu-sei/pharos/blob/master/tools/ooanalyzer/ooanalyzer.pod) | Tracks object pointers and uses logic rules to infer class layouts, inheritance, methods and constructors/destructors; exports JSON. The README describes support as 32-bit x86 MSVC, relevant to this target. | Potentially novel for member/constructor evidence beyond RTTI. Heavy detour: [installation](https://github.com/cmu-sei/pharos/blob/master/INSTALL.md) recommends a container or Ubuntu-oriented dependency build; upstream notes portability is not widely tested. Large binaries can be expensive and incomplete analysis/optimization, aliases and mistaken boundaries can yield false associations. Treat JSON as candidate facts requiring reference and source verification, never direct placement. No runtime/memory estimate or locally verified compatibility is available. |
| [CERT Kaiju](https://github.com/CERTCC/kaiju), [OOAnalyzer importer](https://github.com/CERTCC/kaiju/blob/main/docs/OOAnalyzerImporter.md) | Imports Pharos JSON and applies recovered symbols/types to Ghidra; it is an importer, not an independent OOAnalyzer replacement. Upstream lists version-specific Ghidra/JDK/Z3 dependencies. | Additional setup for visualization only; not needed to parse OOAnalyzer JSON in a private comparison. Since applying it mutates a Ghidra project, isolate the project and keep exported records separate from accepted source. No reason to install it before OOAnalyzer demonstrates unique useful evidence. |
| [Clang LibTooling](https://clang.llvm.org/docs/LibTooling.html) and [compilation database](https://clang.llvm.org/docs/JSONCompilationDatabase.html) | Parses translation units with explicit compile commands and exposes AST/source locations; can collect declarations and relationships for source-side grouping. | Potentially the lowest-cost *new* extraction for actual source-view conflicts, but the project's VC2008/MS extensions, include guards, packing, generated declarations and flags must be faithfully represented. A modern Clang parse or layout is a lead, not proof of VC2008 ABI/emission. Probe a small fixed set before implementing an importer; preserve exact command, diagnostics, tool version and source hashes. Do not rely on lexical class-name matching or assume every original MSVC command works unchanged. |

## Minimal sample benchmark, not yet run

Use four existing cases with different failure modes: TESContainer (unit 775 and owner 980, including the canonical header), BGSBodyPartData/TESModel (units 620/621 with competing inheritance/destructor views), hkpConstraintViewer (unit 2501, graph and destructor uncertainty), and a template/destructor case already identified by the local census. Read the corresponding existing reports rather than rerunning large scans. For each, freeze exact recipe, source/header closure, reference and object hashes; record baseline facts and unresolved fields/slots before using any external tool.

First compare a small Clang AST extraction against existing source declarations under the exact available command context, measuring setup and elapsed time and recording every parse failure. If a pre-existing isolated Ghidra environment is available, independently export only the same classes and compare newly supported facts against the local RTTI/COFF inventory. Do not add OOAnalyzer/Kaiju unless that comparison leaves a specific class question they plausibly answer and its setup is separately authorized. Count unique source-backed facts, independently confirmed facts, conflicts, parse failures, and accepted-generator candidates separately; record wall time and manual/model effort. Stop the route if it only duplicates known RTTI or requires guessed aliases. None of these source or binary hypotheses bypasses current compiler, relocation, EH, image and gameplay gates.
