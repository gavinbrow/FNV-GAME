# NiRefObject native identity and class-key scope

The reference NiRefObject TypeDescriptor at 0x011854e0 names `.?AVNiRefObject@@`. Its primary RTTI locator is 0x01107a6c, and the observed relocated code-pointer prefix at 0x0101dce4 contains two entries: 0x004968e0 and 0x00cfcc20. The hierarchy contains NiRefObject at PMD 0 and `.?AUNiMemObject@@` at PMD +4, both with the observed nonvirtual PMD/attributes recorded in the class census. These are observed records and a code-pointer prefix, not proof of an entire class ABI or table extent.

The public `NiRefObject.h` declares a virtual destructor, `DeleteThis`, and a four-byte reference count at +4; its size assertion is eight bytes. Unit 1484 owns the source-native `NiRefObject::DeleteThis` at 0x00cfcc20, whose original code dispatches slot 0 with delete flag 1. The reference slot-0 deleting wrapper at 0x004968e0 belongs to unit 612's surrogate and calls the separately owned 0x00496910 destructor view, then conditionally frees eight bytes using 0x00aa1460. The 0x00496910 view installs the reference table and decrements the counter at 0x011f4400.

A separate optimized destructor view at 0x00a5d3d0 is presently owned by unit 2725. Existing unit 1503 naturally emits `NiRefObject::~NiRefObject` from its inline source body; its 18-byte COFF function strictly matches that optimized address and its vtable/counter/atomic relocations. This is an owner lead, not an approved transfer: 0x00496910 and 0x00a5d3d0 are distinct reference functions and must remain distinct until native identity, code ownership, COMDAT and final resolution are proved. Unit 1503's emitted scalar-deleting fallback is 42 bytes, whereas the original slot-0 wrapper is 46 bytes, so the fallback must not be bound to that reference slot by name alone.

The existing unit-1503 object emits the correct two-slot count and NiRefObject root name but the wrong base type name, `.?AVNiMemObject@@`, while the original is `.?AUNiMemObject@@`. The public `NiMemObject.h` defines `class NiMemObject`; additionally, `include/layout_support.h` forward-declares it as class before that definition. PMD +4 matches in the observed object. Both class-key declarations must be considered together in an isolated test; changing only the definition does not establish the emitted RTTI spelling.

The private `nirefobject_classkey_stage.py` fixture tests changing both public declarations to `struct` in the existing unit 1484 and 1503 source contexts. It does not alter live files or force symbol emission. The two contexts total 13 mapped functions and require `/showIncludes`, original/candidate functions and EH, emitted graph/PMD/slot and symbol/COMDAT checks. This is not a complete integration cohort: `layout_support.h` is shared broadly and many independent NiMemObject definitions and class-key forward declarations occur in other source contexts. All affected include closures and first-declaration histories must be assessed before a public-header change.

The constructor currently appears as an inline public-header definition that zeroes the refcount and increments the static count; no independently owned original native constructor has yet been established. No inferred constructor address, global RTTI placement, table ownership, complete class recovery or runtime claim is made. Machine-readable local evidence is in `out/phase2-nirefobject-native-evidence.json`.
