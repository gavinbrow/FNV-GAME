# NiMemObject allocation API hypothesis

The original NiRefObject slot-0 scalar-deleting wrapper at 0x004968e0 is a 46-byte /Od source-owner view. It calls 0x00496910, then on the delete flag passes both `this` and size 8 to 0x00aa1460. Unit 612's separate NiMemObject source view declares `operator new(unsigned int)` and sized `operator delete(void*, unsigned int)`; its recipe binds those to 0x00aa13e0 and 0x00aa1460. Unit 1664's source-owned 0x00aa1460 body forwards the pointer and size to the current allocator manager's scalar-deallocation operation.

The existing unit-1503 /O2 native NiRefObject scalar-deleting fallback is 42 bytes. Its destructor work is inlined, and its conditional release emits a one-argument relocation to global unsized `??3@YAXPAX@Z`; common recipe bindings associate that spelling with 0x00401030, but final link resolution has not been established for this private object. Both allocation semantics and optimization shape differ. Declaring sized delete may alter the former; it does not by itself prove that the /O2 42-byte wrapper can own the original /Od 46-byte body.

The public `NiMemObject.h` is currently an empty class with size one and no allocation declarations. The independent private `nimemobject_allocation_api_stage.py` proposal adds only static class `operator new(unsigned int)` and sized `operator delete(void*, unsigned int)`; static declarations do not add instance fields. It retains the current class key and is separate from the class-key-only proposal. Proposed allocator/deallocator recipe names and addresses are diagnostic metadata; no bindings or source edits are installed.

The complete static quoted-include over-approximation for this one header includes 126 recipe units, 2,534 mapped functions and 88 listed EH tails. Some lexical includes may be inactive; class-specific allocation and deallocation changes can affect code, unwind cleanup and emitted deleting wrappers in any active consumer. The private two-unit mirrors cover only 1484/1503 and cannot establish the entire change. Require actual COFF class-new/delete symbol emission and all affected function/EH/metadata comparisons, scope-specific previous declarations, source-backed allocator signatures and release ownership, original/reference wrapper comparison under matching compiler flags, weak fallback/COMDAT resolution, production labels, final image and runtime gates.

The staging source view for 0x00aa13e0 uses a guessed `void(int)` signature. Its dispatch behavior and existing unit-612 binding are evidence for the lead, not independent proof of the original allocator's complete C++ signature or return semantics. No claim is made that this hypothesis identifies the full native class or final linkage.
