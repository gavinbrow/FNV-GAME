# Unit 260 RefPtr EH identity audit

The archived d569 unit-260 object defines exactly one `??1RefPtr@@QAE@XZ`, a 33-byte body. Its full body and IAT relocation independently match the unit-1515 source-recipe function at 0x00b66f20. The body is not byte-identical to the independently mapped 29-byte functions at 0x0045cec0 or 0x0044cbf0.

The original-parent-anchored EH section for `FUN_00c7d900::~FUN_00c7d900` contains three relocations to that one local decorated name. Their compiler-side cleanup thunks use `this + 0x84`, `this + 0x250`, and `this + 0x2a4`; the corresponding original control-flow targets are respectively 0x0045cec0, 0x0045cec0 and 0x00b66f20. The first target has an independent unit-386 source recipe owner: a no-argument thiscall wrapper that checks its pointee and calls `SeqObj::FUN_00401970`. The other target has an independent unit-1515 source recipe owner and the same complete body/relocation as the emitted RefPtr destructor. The 0x0044cbf0 global same-name association is a different 29-byte source function; it cannot correctly resolve these three sites.

The existing unit260 source declares all three fields as `RefPtr`, and explicitly calls `Reset()` on +0x250 and +0x2a4. A possible repair is to give the first two fields a distinct unit-local wrapper type whose destructor faithfully emits the source-backed 0x0045cec0 behavior, retain the current RefPtr semantics at +0x2a4, and preserve existing Reset behavior and field layout. This is a hypothesis, not a supported installation: the pointee types and `FUN_00401970` semantic identity are not established, and changing destructor types may alter normal parent code, EH state layout, local RTTI or other compiler output. An isolated candidate must compare all affected unit260 functions, both full destructor bodies and all relocations, original EH/xdata mappings and state transitions, field offsets, and every affected caller. A normal source-backed ownership/placement proof is required; the original reference call target alone does not justify a global alias or injected address.

Related unit258 and unit370 sections contain repeated local surrogate names whose original cleanup targets differ. Parent-anchor inspection supplies leads only; exact xdata-derived piece placement and source identities must be established before selecting new owners. Unit253 has an implausible target under a naive linear section-base calculation, so its alternate piece placement must be resolved independently.

The first unit260 split candidate and its forced-inline-Reset v2 were compiled privately and both failed the parent gate (822 original bytes versus 786 candidate bytes). Disassembly shows the 36-byte reduction is two normal automatic destructor cleanups: at original offsets +0x207 and +0x2f7 the reference-count decrement and virtual-release sequences are inline, whereas the candidate emits shorter calls to `RefRelease260::FUN_00401970`. This is not a failure to inline `Reset`; the earlier explanation was incorrect. A future source reconstruction must account for the different normal inline and exception cleanup behavior without binding the 12-byte optimized helper to the 29-byte standalone source owner by address alone.
