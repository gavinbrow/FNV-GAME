# Native constructor hypothesis and remaining class work

`bgsbodypart_psa_native_proposal.py` creates the private native-constructor hypothesis under `out/phase2-bgsbodypart-psa-native-proposal`. It checks input hashes, replaces the explicit base-constructor call and manual vptr store with an empty `TESModelPSA::TESModelPSA()` body, and records the proposed native constructor and destructor recipe bindings. Its manifest contains the actual relocated reference EH chain, all seven state/action pairs, and hashes and relocation facts for the saved original and candidate COFF cleanup sections. It also verifies the reference state-6 instruction sequence and target. Nothing is compiled or installed by this generator.

The constructor is an ABI hypothesis: the compiler must generate the base call and the PSA vptr store exactly, and the resulting native table must match the original. Unit 620's opaque `TESModel` has seven placeholder virtual declarations, not proven native signatures. Unit 621 derives `TESModel` from `BaseFormComponent` and supplies named data fields, but does not declare all of the observed model virtuals. A shared header must first reconcile the true base hierarchy, method signatures and inherited virtual order without changing field offsets or special-member behavior. The original PSA table's first seven code pointers are observed, not a proven complete extent: the following word is also a code pointer. Neighboring ownership and the actual boundary must be established before defining a complete canonical virtual interface. Do not infer a slot signature from its address.

The existing 15+10 function and original EH results belong to the earlier member-only experiment, not this new constructor hypothesis. The latter requires fresh compiler output, exact native symbol and relocation checks, both unit comparisons, complete constructor unwind checks, reference vtable/RTTI and prefix comparison, and independent full-image gates before any acceptance.
