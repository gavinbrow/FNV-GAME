# Type and Xbox mapping research — 2026-11-19

## What is immediately useful

The [PDB naming report](https://github.com/momusdigital/fnv_decomp/blob/main/PDB_NAMES.md) links to the separate [mathisto mapping branch](https://github.com/mathisto/fnv_decomp/tree/pdb-names-mapping). Its JSONL records are a practical, reviewable source of **candidate names and type clues**, including classes without PC RTTI. They do not by themselves establish PC object layout, a correct native inheritance tree, executable vtable ownership, or a complete source implementation.

Two concrete cross-checks were possible without downloading a database:

* [AutoMemContext field record](https://raw.githubusercontent.com/mathisto/fnv_decomp/pdb-names-mapping/fields.jsonl): Xbox retail type information identifies its offset-zero `MEM_CONTEXT` field as the previous memory context. The local `fnv_decomp/include/AutoMemContext.h` already has the corresponding offset-zero field and 4-byte size assertion. This supports the semantics of the one-word local investigated in unit 211, but does **not** resolve its observed PC stack-frame or EH code-generation mismatch. The existing local PC RTTI census has no AutoMemContext type descriptor; absence from that RTTI census is expected to be inconclusive for a non-polymorphic type.
* [Class mapping record](https://github.com/mathisto/fnv_decomp/blob/pdb-names-mapping/classes.jsonl) identifies the existing local `FUN_004aa3d0_shell` in `fnv_decomp/src/fallout_shared/bgstextureusemap.cpp` as a `BGSTextureUseMap` candidate, based on linked Xbox methods. The local file still uses the synthetic shell, while the checked PC RTTI census has no descriptor under that class name. This is a concrete name lead that local RTTI alone did not provide. It is **not** proof that every existing shell/base is the original class or that renaming it preserves the PC ABI. The record's source and evidence fields should be retained, including the actual link methods and any build distinctions.

The mapping schema is directly inspectable: [classes.jsonl](https://raw.githubusercontent.com/mathisto/fnv_decomp/pdb-names-mapping/classes.jsonl) contains old/new name, evidence, provenance tag, address, source file and line; [fields.jsonl](https://raw.githubusercontent.com/mathisto/fnv_decomp/pdb-names-mapping/fields.jsonl) contains class, offset, old/new names, source location, provenance marker and `pdb_type`. For example, an `AbsorbEffect` field at `0x4c` is identified as `NiPointer<NiNode>`. That is an Xbox-derived candidate for a PC member: verify the local PC field's offset, extent and uses before changing its type. The report documents additional JSONL files for function links, globals, parameters, renamed symbols and parameter-count conflicts. The linked-function file could not be inspected through the browser in this pass; its precise row schema and coverage for either example remain unverified.

Upstream reports 37,460 links across 68,657 PC function addresses, with high/medium/low, two disputed and one rejected links; it reports 4,852 field renames and 72 class renames, of which 50 are already based on PC RTTI and 22 on linked methods. These are the authors' results for their branch and input set, **not measured local coverage or a guaranteed correctness rate**. The authors explicitly describe folded functions, overloads, position-based link drift, differently typed fields, inconsistent parameter counts and naming collisions as limitations. A held-out high-tier estimate is not independent evidence for a particular match. [PDB report, methodology and risks](https://github.com/momusdigital/fnv_decomp/blob/main/PDB_NAMES.md).

## Atlas: richer types, but not locally tested

[FNV source atlas v0.5.0](https://github.com/amarkham23/fnv-source-atlas) documents a schema-8 SQLite corpus and read-only `type`, `class`, `data`, `raw-vftable`, `pc` and `xbox` queries. Its [data model](https://github.com/amarkham23/fnv-source-atlas/blob/main/docs/DATA_MODEL.md) explicitly separates CodeView physical records and type indices from tag layouts, ordered members, method overloads, typed Xbox globals, PC/Xbox match hypotheses and review decisions. It can preserve field types, member offsets, base/layout information, access/method attributes, potential vtable offsets and typed globals rather than just names. It also preserves incomplete type-server references, diagnostics, folded-address alternatives and non-entry targets. These are documented capabilities; no atlas database was downloaded, opened or queried in this investigation.

The database's type/layout records are principally Xbox debug information. Cross-platform class sizes, padding, access, virtual slots, compiler conventions and addresses must be checked independently against the PC executable and the exact source/compiler context. Atlas slot alignments are hypotheses; code-derived candidate matches can depend on the same anchors and should not be counted as independent corroboration. The project's software license does not grant rights to its PDB-derived data or third-party artifacts. Its published database is about 752 MiB compressed and 3.93 GiB extracted; obtaining it would be a separate decision, not a necessary first pilot. See the [atlas README and release description](https://github.com/amarkham23/fnv-source-atlas/blob/main/README.md).

The separate [Xbox project](https://github.com/ieee802dot11ac/fnv) targets an Xbox 360 release MemDebug executable and is a work in progress. Its source and build target are not an exact PC retail replacement; its maintainers also expressly ask that AI software not be used to decompile its game code. This report relies only on its publicly stated scope, not on incorporating its code.

## Existing local evidence and a bounded pilot

The exact checked paths `fnv_decomp/PDB_NAMES.md`, `fnv_decomp/classes.jsonl`, `fnv_decomp/fields.jsonl`, `fnv-source-atlas/build/fnv-source-atlas.sqlite`, and `atlas-data/fnv-source-atlas-data-0.5.0/fnv-source-atlas.sqlite` were absent; this is **not** a claim that no copy exists elsewhere. The local checkout lists only `main`, `codex/playable-rebuild`, and `origin/main`; no mapping branch was fetched. Existing `runtime-next/m3/out/phase2-class-census/census-v2.json` does contain PC RTTI class/locator observations for TESContainer and BGSBodyPartData. No broad directory search, queue mutation, build or data download was performed.

The smallest useful next pilot is a **two-case, read-only comparison**: (1) AutoMemContext's mapped old-context field versus the local header and unit-211 PC frame/EH evidence; (2) BGSTextureUseMap's linked-method class claim versus the local `FUN_004aa3d0_shell` definitions and exact mapped PC functions. For each, record the upstream row and its origin, local pre-existing fact, any genuinely new fact, PC corroboration, ambiguity and decision. A successful result would be a reproducible evidence table with explicit changed/unchanged/unknown counts—not a source rename. If these two records add no discriminating evidence, stop before creating an importer. If useful, extend to the existing 20-class benchmark in the earlier memo and separately decide whether acquiring the atlas is warranted.
