# M3 phase 1: DAT_ globals defined in our source (design, 2026-11-16; read-only investigation, nothing built or edited)

Read: build_all.py, data-v1 (phase0/place/report/NOTES), data-v3 (gen/common/verify/postproc/dump_pieces/NOTES), layout-v2 (make_image/snapshot), link-v2 (NOTES, prep3 behaviour), data-v2/PLAN.md, pinned-build/assemble_v3.py (resolver), units.json, a few source files.

## 0. Two facts that change the framing
1. **The default build has no link step.** `build_all.py` never runs link-v2. The name -> address mapping for externs is done by `assemble_v3.resolve_field` (used by build-v7 and data-v1/phase0). `D_<va>` labels exist only inside data-v3's MASM objects and in link-v2's rewritten objects.
2. **data-v1's "ours" bytes never reach the exe.** `make_image.py` takes every data byte from `data-v3\out\*.obj` (reference-captured literals + symbolic `dd offset` fields). data-v1 placement only feeds counters (`progress.json`, `produced_pieces.json`, `produced_ranges.json`, the `ours` flag in `symbolic.json`). So phase 1 is the first time any data byte of the exe would come from our compile; it needs a splice in make_image, not just a counter change.

## 1. How a DAT_ extern resolves today
- Source: `extern int DAT_01032748;` in a `.cpp` (global namespace) compiles to the undefined COFF symbol `?DAT_01032748@@3HA` (C++ mangling: `3` = variable, then the type code, `A`/`B` = non-const/const). `extern "C"` or C-style declarations give `_DAT_011dcfa4`. Many units wrap code in `namespace fnv_xxxxxxxx`, giving `?DAT_01023128@fnv_0087e130@@3NB`: the same VA appears under many mangled names. By my count of units.json symbol keys: about 9,587 VAs with a global-namespace `?DAT_..@@3` name, 1,410 `_DAT_` names, 23,703 mangled-name entries in total (this is the ~15k-extern population).
- Resolution (`pinned-build\assemble_v3.py resolve_field`, priority a..f):
  a) function defined in the unit / `G['fn']`; b) none; c) **`unit['symbols'][name]`** (units.json per-unit map, symbol name -> address, e.g. `'?DAT_01032748@@3HA': '0x01032748'`) then global `G['sym']` (`recipe_names`); b) **`ADDR_RE` embedded address** `(FUN|DAT|PTR|LAB|SUB|UNK|OFF|BYTE|WORD|DWORD|switchD|caseD|LOC)_<8 hex>` anywhere in the name (not for `__ehhandler$`-type prefixes, not when preceded by `$<digit>?` = template argument, only inside 0x400000..0x147b000); d) imports.
  So the *name is the address*; the mangled type is irrelevant to resolution. build-v7 turns it into `relocs_v7.tsv.gz`; layout-v2 maps the original VA to the new VA (`Lall/Lone`).
- Which tool maps it to `D_<va>`: only **link-v2** (`prep3.py` using `symaddr.json` from `FNV_DUMP_SYMADDR=1`, rewrites undefined data names to `D_<va>` and removes data sections that data-v1 placed). Not in `build_all`. data-v3's `D_%08x` labels are created at every pointer-field target (`gen.py`), plus extra ones with `DV3_CNAMES=1` (link-v2 only).
- Collision of a source definition with the same name: in the default build nothing links, so **no collision is possible**; duplicates only matter to (a) link-v2 (LNK2005; 4,546 non-COMDAT duplicate definitions already exist because variant units define the same globals; rule "one defining unit per address"), (b) data-v1 `State.rebuild_gdef` (name -> address dict built from placed public definitions: a generated definition adds the same entry, harmless if the VA agrees), (c) a future real link (generated definition + 167 source definitions + extern users must collapse to one).

## 2. The existing source definitions of DAT_ globals
My regex over `fnv_decomp\src` (.cpp/.h, no .bak): about 167 non-extern definition lines in 106 files (72 `static`, 86 with initializer, 69 `const`; the "286" figure is probably a looser pattern). Examples: `float DAT_011f1bf0;` (actor.cpp:32763), `const float DAT_0102b3c8 = 3.14159f;` (actor.cpp:98630), `InterlockedCompareExchange_t DAT_00fdf1bc = InterlockedCompareExchange;` (blk_00420000_od.cpp:3467, two variant files too).

Traced, `DAT_00fdf1bc` (unit 2629 = src/staging/blk_00420000_od.cpp, flags /MT /Od /Oy- /GS /EHsc /Gy, compiler sp1):
1. `compile_units_v3` -> `pinned-build\obj_v3\2629.obj`: non-COMDAT `.data` section idx 4, 4 bytes, public symbol `?DAT_00fdf1bc@@3P6GJPCJJJ@ZA` value 0, one DIR32 reloc.
2. build-v7 ignores the data section; code that uses the symbol resolves it by units.json map -> 0x00fdf1bc (rule c).
3. data-v1 `phase0.py`: section recorded with hint `(0x00fdf1bc - 0, 'unit-map', name)`; the DIR32 resolved by `resolve_field`.
4. `place.py`: kind `data-unit`; no unmasked bytes (all four are the reloc), so tier B has nothing to search; tier H verifies at the hint address -> placed at 0x00fdf1bc, tier H (`pieces.tsv.gz` row `00fdf1bc 4 H data-unit`).
5. `report.py`: counted as produced only if our resolved field value equals the reference.
6. data-v3 `dump_pieces.py` -> `produced_pieces.json` -> `postproc.py` -> `produced_ranges.json` and `our_symbol` alias on label `D_00fdf1bc`. **Nothing else**: the exe bytes are data-v3's captured `dd offset C_...`.
Zero-initialized definitions (`float DAT_011f1bf0;` -> `.bss`) are recorded with a hint but `place.py` excludes kind `bss` ("layout only"); `const`/`static` ones are usually folded into `__real@` COMDATs or internal symbols (storage 3, filtered by `d[2] == 2`), so they are never "ours" under their DAT name.

## 3. Minimal pipeline change, opt-in `FNV_M3=1` (default build byte-for-byte unaffected)
Principle: **data-v3 keeps owning the section layout; the generated object overlays exact byte ranges at their original offsets.** Because chunks keep original offsets, no moving or padding logic is needed.

New folder `runtime-next\m3\`:
- `gen_m3.py` (reads only `data-v3\common.py` = reference + original .reloc, and units.json; no dependency on a previous data-v3 run):
  - collects `DAT_<va>` declarations, picks the selection (section 5), emits `m3_data.cpp`: `extern const float DAT_01017b78 = 10.0f;` (const iff VA is in .rdata) / `float DAT_011e07dc = 1.5f;`; writes `m3_manifest.json` (symbol, va, size, type, expected section, pointer fields `[off, target_name, addend]`) and `skip_ranges.json` (`[[va,size],...]`, the format `DV3_SKIP` already reads).
  - compiles with the same cl and flags as units (sp1, `/MT /Od /Oy- /GS /EHsc /Gy`), same obj format.
  - **self-pruning loop**: for every manifest entry, slice the object (by symbol -> section index + value + size, not by section name: this handles COMDAT or per-symbol sections), compare with the reference bytes (pointer fields masked); entries that differ (float literal rounding, wrong size, padding assumption) are dropped and the file recompiled until stable. Also fails if the obj has any `.CRT$XCU` section or `??__E` symbol (dynamic initializer), or if the section name of a symbol disagrees with `.rdata` vs `.data`.
- `splice.py` (shared library): `load(objpath, manifest) -> [(va, bytes, relocs[(offset, symname, addend)])]`, resolves symbol names to original VAs: defined in the m3 obj -> manifest VA; else `ADDR_RE` embedded address (`_FUN_00401234`, `_DAT_...`); else `code_symbols.json`. Asserts reloc offsets equal the original .reloc sites inside each range.
- `m3secs.py` (data-v1 pseudo-unit, modelled on `data-v2\libsecs.py`): one record per global in phase0's format (`name '.data'/'.rdata'`, `data`, `relocs` with `rsrc/rexp` pre-resolved to ('b', va+addend), `defs=[(sym, 0, 2)]`, `hints=[(va, 'm3-name', sym)]`, extra key `forced=va`, `kind0='m3-global'`). Unit id 200000.

Changes to existing files (each behind the env var):
1. `build_all.py`: if `FNV_M3=1`, run `python -I m3\gen_m3.py` as a new step right after step 1 (needs only cl; before data-v1) and add `DV_M3=1`, `DV3_SKIP=<m3\skip_ranges.json>` to `env`. build_all passes `env` to every step, and the .cmd files inherit it, so no .cmd edits. Record the m3 counts in `build-summary.json` provenance.
2. `data-v1\place.py`: in `build_state`, `if os.environ.get('DV_M3')=='1': P0.update(m3secs.m3_units())` (next to the `DV_LIB` hook); `s['kind'] = s.get('kind0') or kind_of(s)`; in `run().round_`, before the tier-B search: `if s.get('forced') and verify_at(s, {}, s['forced']): place(k, s['forced'], 'M'); continue`. That is placement by name/address hint, independent of byte uniqueness (B would otherwise mis-place a 4-byte scalar or say 0 hits). `report.py` needs only the tier legend entry; its produced-byte and per-kind counters pick the pieces up through `placed`. `dump_pieces.py`/`postproc.py` need no change: M pieces flow into `produced_pieces.json` and `produced_ranges.json`.
3. `data-v3\gen.py`: no code change; `DV3_SKIP` already zeroes the ranges and drops the pointer fields inside (labels `D_<va>` are still emitted at their offsets if other fields target them, so other captured tables that point into a generated global still resolve). `data-v3\verify.py` (round trip) will report DIFFERENT for the zeroed ranges: add 6 lines that overlay `splice.load()` bytes/relocs before the comparison when `DV_M3=1` (verify does not set an exit code today, so also make it `sys.exit(1)` on FAILED). `rebuild.cmd` already `|| exit /b 1` after it.
4. `layout-v2\make_image.py`: after the "data objects" loop (where `chunks[...]['data']`, `['relocs']` and `alladdr` are built): `if FNV_M3: for va, blob, rels in splice.load(...): ch = chunk containing va; ch['data'][o:o+len(blob)] = blob; drop ch['relocs'] with offsets inside; ch['relocs'] += rels; alladdr[name] = va-of-name for each new symbol`. The existing rewrite loop (`va = alladdr[nm] if nm in alladdr else csym[nm]['va']`, `Lone(va)+add`, `data_sites.append`) then rewrites the pointer fields to new addresses and emits the .reloc sites. `snapshot.py`: also copy `m3_data.obj`, `m3_manifest.json` into the snapshot (make_image reads only the snapshot's data-v3 copy).
5. Optional honesty switch: because SKIP zeroes the captured bytes, the exe can only equal the reference if the compiled bytes are right. Run once with a deliberately wrong initializer to prove the bytes are live (sha must change).

Nothing in units.json, build-v7, pinned-build/compile_units_v3, or the unit sources changes. Existing `extern ... DAT_x` declarations keep working through the name->address rule; they are not rewired to our definitions until M4 (real link: link-v2 `prep3` would rename our generated symbols to `D_<va>` like every other data name).

## 4. Pitfalls
- **Alignment/padding**: slice exactly `sizeof(T)` bytes at the symbol, never the section; padding between globals (compiler alignment inside our obj, original linker padding in the reference) stays data-v3 literal. Section alignment of the obj is irrelevant for the splice (address comes from the name) but matters for M4: a `double` in the reference at VA%8 != 0 would be a sign the type is wrong (check `va % align == 0` in the generator).
- **Zero initializer**: `int x = 0;` / `float y;` go to `.bss` in cl, not `.data`. File-resident zero globals in `.data` (77,661 zero bytes, many are such) cannot be produced by the plain definition; skip zeros in phase 1 (generator excludes all-zero ranges). Real .bss globals (714,908 B virtual tail; 3,111 scalar-typed VAs) are layout-only: phase 2 with `#pragma bss_seg` or a layout record, not bytes.
- **const vs non-const**: constness is chosen from the VA's section, not from the declaration (decompiled externs are often non-const for `.rdata` data). A `const` object needs `extern const T x = v;` (plain `const T x = v;` has internal linkage in C++ and is dropped or emitted as a local symbol; plain non-const goes to `.data`). The generator checks the obj section name against the VA's section; a mismatch is dropped.
- **Mangling**: irrelevant for the splice (name-embedded address). For M4 it matters: namespaced variants (`?DAT_..@fnv_xxxxxxxx@@3NB`) and const/non-const (`A`/`B`) variants of one VA all exist; the link route must collapse them by address (link-v2 prep3 does) and not by name. Template-argument forms (`$1?DAT_..`) are parameters, not locations (the resolver already refuses them). Use `extern "C"` names (`_FUN_<va>`, `_DAT_<va>`) for pointer targets inside generated initializers; that avoids having to spell C++ types of functions.
- **COMDATs**: VC2008 `/Gy` applies to functions only; plain globals go to unit-level `.data`/`.rdata` sections, but a `selectany`/inline/template-static could create COMDAT sections. The slicer works per symbol, so both cases are handled; `place.py` keying (`keyof`) for non-COMDAT pseudo-units is `('u', unit, k)`, unique.
- **One DAT_ is a field/part of a bigger object**: the decompiler declares `DAT_x` int but real data may be an array or struct whose other members are declared as separate DAT_ at other VAs, or accessed as `&DAT_x + n`. Slicing the scalar is still byte-exact, but (a) reject entries where another declared DAT_ VA or a `D_` label/pointer-field target lies strictly inside `(va, va+size)`, (b) reject type conflicts (117 in .data, 155 in .rdata across units: same VA declared int and float etc.), (c) never merge neighbours into arrays in phase 1.
- **Dynamic initializers**: `unsigned x = (unsigned)&other;` or `int x = f();` becomes a `.CRT$XCU` initializer and the static image holds 0. Use pointer-typed fields for addresses, `reinterpret_cast`-free constant initializers only, and let the generator fail the step if the obj has `.CRT$XCU`/`??__E`/`$E` symbols. No constructors, no classes with non-trivial members.
- **Pointer fields**: only emit a relocation where the original .reloc says so (`drel`); the 7,126 look-alike integers must stay integers (the 54 `(unsigned)&DAT` integer constants of reloc-v5 are the same trap). Cl emits DIR32 for `&sym`; make_image already handles kind 6 only (asserts).
- **Floats/doubles**: emit `%.9g`/`%.17g` and let the prune loop catch compile-time conversion differences (VC2008's decimal-to-binary can be off by an ulp); skip NaN/Inf/denormals. `-0.0` must be written `-0.0f`. `__m128` unions and `__real@` pooled constants are out of phase 1 (pooled COMDAT constants are already ours via data-v1).
- **Strings / char arrays**: size is unknown from `char DAT_x`/`const char* const` declarations (the type is the decompiler's guess); the 166 `char`-typed and 577 pointer-typed .rdata candidates without relocation are strings or tables. Exclude in phase 1.
- **Duplicates with existing source**: skip any VA that already has a source definition (167 lines) or that data-v1 already placed from our objects (`produced_ranges.json`: 566 of the .rdata candidates are already ours). Variant units (`*_variant.cpp`) repeat definitions: do not touch them in phase 1.
- **data-v3 labels**: gen.py raises "label strictly inside a field" fixes; keep SKIP ranges away from existing pointer fields (generator rejects entries overlapping `fields`).

## 8. Phase 1b investigation: globals that hold pointers (read-only measurement, 2026-11-16; nothing built)
Measured over the global-namespace `?DAT_<va>@@3<T>` VAs in `.data`/`.rdata` (extent = gap to the next declared DAT VA, capped at the section's raw end) that contain at least one original-.reloc field (`symbolic.json` fields; 150,462 fields in all: 88,036 to functions, 48,716 to data, 11,109 other code, 2,567 piece). Script: session scratchpad `p1b.py` (not kept in the repo).

| shape | .data | .rdata | notes |
|---|---:|---:|---|
| single pointer, exact 4 B (`P..` type, field at VA, no other field) | 47 ptr-to-data (`PBD`/`PAD`...), 8 ptr-to-func (`P6AHHH@Z`, `P6AP..@Z`) | 1 ptr-to-data, 0 func | 4 B each; targets: 44 `.data` -> `D_` labels (data), 3-4 `.data` -> functions; .rdata singles are int/`PAPAX`-typed |
| int/unsigned-typed scalar that is really a pointer (`H`/`I` with a field at VA) | 6 exact 4 B (+31 with a larger gap) | 5 exact (+215 with a larger gap, of which many `M`/`N` typed: wrong declared type, the gap is a struct) | the declared type is wrong; emit as pointer or `unsigned` + `(unsigned)&sym` (dynamic init: avoid) |
| pointer arrays / tables (`PAU..`, `PAPAU..`, `P6AXXZ` x N, `QBD` string-pointer tables) | 103 data-ptr + 5 func-ptr tables (the biggest: 356 fields, 2,852 B) + 6 `QB*` | 197 data-ptr + 4 func-ptr + ~115 `QB*` tables | array length is not known from the declaration: derive from the gap and the field pattern; most `.rdata` ones are vtable-like or string tables |
| scalar-typed VA with many fields inside (`H`/`D`/`E` extent holding several pointers: arrays/structs the decompiler typed as a scalar) | 124 | 1,479 (e.g. 0xff0000 `H`, 5,454 fields: an `.rdata` blob; VA = section start, effectively a whole data piece) | not 1b scope, handle as table pieces (see data-v1 `place.py` units) |
| structs mixing pointers and scalars (`U`/`T` types) | 4 | 8 | `UAudGuid`, `UPixelTemplate`...: need the type; defer |
| multi-type VA (same VA declared as different types) with fields | 88 | 183 | excluded by the single-consistent-type rule |
| already has a source definition | 1 | 17 | skip |

Target kinds of all single-pointer candidates (pointer-typed or int-typed VA with a field at the VA, none at +4, no source def, one consistent type): .data 44 -> `D_<va>` data labels (all the same label in the first examples) and ~5 -> functions; .rdata ~46 -> functions (mostly `H`-typed vtable-ish/destructor slots `?Destroy@..`, `?FUN_..`) and 3 -> `C_00ec60fa`-style code labels. So the first slice of 1b is about 100 single pointers; the ~300 tables (and the QB* string-pointer tables, ~120) are a second slice.

What each stage needs for relocations:
- `gen_m3.py` emit: pointer fields as `extern "C"` declarations of the target, `extern "C" void _FUN_<va>(); extern "C" char _DAT_<va>; ... T* DAT_xxx = (T*)&_DAT_<va>;` (a plain address-of constant is a static initializer with a DIR32 reloc, no `.CRT$XCU`). Functions that the recipe defines under a mangled name are better targeted by `_FUN_<va>`/address name than by C++ mangled name (splice resolves it via ADDR_RE). Addend: target+offset as `(char*)&_DAT_x + n`; field value minus target VA gives the addend (check `bytes == target VA + addend`). Per-entry self-check changes: the sliced bytes are compared with pointer fields masked (the 4 bytes of each DIR32 are the addend, so compare `ref_value - target_va` to the object's addend bytes), and the object's relocations must be exactly the original .reloc sites inside the range (offset set equality), each with a resolvable symbol. The manifest gets `fields=[off, target_sym, addend]`.
- `splice.py`: relax the "no relocation" assert; `load()` returns `relocs[(offset, symname, addend)]` with symbols resolved to an original VA (m3 symbol -> manifest VA; `_FUN_`/`_DAT_` name -> embedded address; `D_`/`C_` data labels -> VA; code symbols via `code_symbols.json`); assert offsets equal original .reloc sites, and kind is DIR32 (6).

### Synthetic file-backed zero object (2026-11-18)

A temporary, original C++ fixture compiled with local VC2008 SP1 demonstrated a supported `.data` route:

```cpp
#pragma section(".data", read, write)
extern "C" {
unsigned char neighbor[4] = {1, 2, 3, 4};
__declspec(allocate(".data")) __declspec(align(4)) unsigned char file_zero[16] = {0};
__declspec(align(4)) unsigned char memory_zero[16] = {0};
}
```

The compiler warned C4325 that standard `.data` attributes were ignored. The explicit allocation nevertheless produced an initialized `.data` section containing exactly 16 zero bytes, flags `0xC0300040` (4-byte alignment, initialized read/write data), with no relocations. The ordinary zero definition instead produced a 16-byte `.bss` section, flags `0xC0300080` (uninitialized read/write data), with raw-data pointer zero. The non-zero neighbor and `file_zero` occupied separate `.data` sections; the latter did not require the neighbor for its file backing. This synthetic checkpoint established a compiler/reader technique only: no target range, end-to-end placement, linker behavior, or original bytes had yet been verified. A follow-on synthetic loader check found that `compare.Coff` synthesizes zeros for raw-less uninitialized sections.
